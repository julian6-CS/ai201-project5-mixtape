Describing how a users' listening now feed is populated: When a user views or accesses the feed to see what their friends are listening to, a request leading to the "/<user_id>/listening-now" route is placed for a JSON response containing a list of ListeningEvents. The endpoint then calls the get_friends_listening_now() function provided by the feed_services.py file with the user_id as a parameter. The get_friends_listening_now() function retrieves the User object from the database, if there is is entry associated to the user_id it will raise a ValueError. Otherwise, it will calculate a time cutoff where entries made before this cutoff will not be requested. Using the user object retrieved earlier, the friends list will be retrieved from the friends variable so it can then request all the listening events stored in the database associated with one of the friends in the list and created after the cutoff time. This list of listening entries is then cleaned to only contain the one most recent listening event per friend. A list of dictionary objects containing the friend id, the song, and the time they listened to the song is returned. The endpoint then returns a JSON object with this list labeled as "feed: and the size of this list as "count". I presume that this list is then propogated to the users view where they can then see what the most recent song their friend has listened to in the last 24 hours.

To be entirely sure of my decision, I emulated many possible examples and I saw that specifically when a date landing on a Sunday is provided to the update_listening_streak function, the listening_streak variable is set to one in user object associated with the user id used in the function call .

Root cause explanation:

When the update_listening_streak is called it requires a user id and a date defined by the datetime library, this object can then be called so any user can receive a simple explanation of the date like .weekday() which provides the specific day a date lands by returning an int value representing the day. On line 73 within the streak-service.py file there is a piece of broken logic where in order for a users' listening streak to be increased the last accessed day from the user has to be one calendar day away from today. For the streak to increment, it must also be called on any day other than a Sunday or where .weekday() does not equal to 6, otherwise the entry ends up on the else clause where the entries' listening streak is set to 1. I evaluated every function and workflow involved with the listening_streak variable to see if this is expected behavior, arriving to the realization that this is unexpected behavior and the listening streak should continue to increment regardless of the day under the right conditions. This change in the user object is then stored in the database and the error is propogated to everything access the listening_streak variable inside of the user object, displaying incorrect data when get_streak() is called.


Fix description: Within the update_listening_streak function, I had to remove the "and today.weekday() != 6" clause from the "elif days_since_last == 1 and today.weekday() != 6" on line 73, clause causes the listening streak to be set to 1 since entries on sunday fail the clause forcing it into the else statement used to set the streak back to one. This is counter-intuitive because the expected functionality from a streak should only reset if a day is missed and is not dependent on any day at all.

Bug Analysis: Bug 2, "friends Listening Now shows people from yesterday" located in  `feed_service.py` 

Reproduction Steps: Prior to explaining the reproduction steps I would like to say that "replicating_bugs.py" has a method called testing_bug_two() that can be called after seeding the data in this project where this bug is made visible. First and foremost, the last_listened_at variable in each User object and the listened_at variable in each ListeningEvent must be set to a datetime twenty three hours ago from now. After this, any and every user_id will replicate this bug by simply calling get_friends_listening_now with it. The function will return a long list of listening_events that took place yesterday and thus reproducing the conditions neccessary for this bug.

Navigation strategy: At first, I starting looking at everything related or involved with the Listening Now function workflow within the 'feed_service.py', luckily the specificity in the bug description gave me a hint on where to start. This investigation led me to analyzing all the workflows involved with creating or updating the ListeningEvent objects in the database, methods like the record_listening_event function in "streak_service.py" and the songs.py route for behavior involving listening to a song. I first verified the "/<song_id>/listen" route in songs.py and saw that there was no incorrect data being or any behavior that could possibly lead to the bug. This needed to be ruled out since there was always the possibility that an incorrect data entry when calling the record_listening_event function could potentialy lead to the comparison breaking. Then I evaluated the record_listening_event to see directly how the dates were being entered within the user class and within the ListeningEvent objects, the function engaged with the expected behavior and there was nothing that could potentially cause any error. Coming to the conclusion that there is no other potential cause for the bug and engaging with the workflow which would typically cause this error to occur, I narrowed my focus onto the get_friends_listening_now function, specifically to the areas where date or time are being evaluated or logged. I first evaluated programming lines 46-54 and saw that the correct logic is present when querying the neccessary ListeningEvent objects within a certain time threshold. Lastly, I analyzed where this threshold is defined, finding that a rolling time implimentation is used while the user expects a date/time implimentation aligned with calendar days. Logically, this seemed like the culprit since a threshold set 24 hours ago also includes time within yesterday. To be sure of my conclusion, I called the get_friends_listening_now function with a shorter threshold where the cutoff is midnight today and I saw the intended behavior. I also replicated the bug many times to see the effect the threshold had on different users or circumstances. I was now certain that the bug was caused by how the function creates the cutoff time.

Root cause explanation:
There is a local variable called threshold within the 'feed_service.py' file that only the get_friends_listening_now function interacts with. This threshold is used to calculate the intended cutoff time which the database query uses to retrieve all the of the listening_events entries belonging to the users' friends and within the cutoff time by comparing it with the time the event was created. This cutoff time was calculated with a rolling time implimentation in mind, where it was created by getting the time now and simply subtracting the threshold from it. This threshold is defined as 24 hours, so the cutoff time is always yesterday at the same time, including any time between then and 11:59pm of that day. So when this cutoff time was used to compare it against the times the ListeningEvent was created, the query would return objects that subsequently also landed within the 24 hour range but created yesterday. This list of objects were then returned by the get_friends_listening_now function and provided to the user to view.


This error is mainly caused by a miscommunication from the platform to the user on the intended use case for this functionality.

Fix description: It's clear from the bugs description that the user interprets the feeds behavior to be based on calendar days rather than a numerical representation of time. Instead of altering the global variable of Recent_Threshold constant or replacing it, which wouldn't effect any other workflow but it has an established purpose intended by other programmers. I modified the programs behavior to be more closely aligned with the perceived behavior from the users. I achieved this by instead using today at midnight (12:00 am) as the base time instead of the current timestamp. This is supplemented by integrating a 24 hour offset against the Recent_Threshold which would effectively treat the times as calendar days. For example, a 24 hour threshold is treated as exactly today, a 48 hour threshold includes today and yesterday, and so forth. This is placed inside of an if clause in the case that a threshold under 24 hours is defined which would then imply that the behavior should be more aligned with the rolling time format shown originally.

Side-effect check:

After changing the cutoff calculation, I verified that get_friends_listening_now was now returning only friends whose listening events fell within the calender day window. I was able to achieve this by integrating a piece of code that checked every provided entry from the database query on whether it was created today or not. Also, getting all the events created before the cutoff time and verifying whether there was any overlap by using set notation. I also checked if there were any repeated entries or friends after the sorting to see if this change in cutoff could have caused anything. Lastly, I evaluated whether the 'feed.py' route for listening now receives the proper return value and if it can be properly changed in a JSON object. I felt comfortable with this analysis since the cutoff change only affected a timestamp used for a database query; leaving everything in the system unchanged.
